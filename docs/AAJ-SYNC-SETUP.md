# Connecting the "Aj ki List" Google Sheet to the website (Aaj Sync)

This guide is for Dr. Ali. It takes about 10 minutes, once. Staff do not need to do anything.

## 1. What it does

- Staff can enter patients in the **website's Aaj ki List** or in the **Google Sheet "Aj ki List"**. Both lists stay the same. You do not choose a main one.
- A new patient typed in the sheet appears on the website within about 2 minutes, and the other way round.
- A row **with an Mr#** is a patient. The website adds the day's **token** (when the Token cell is empty) and fills in the rest.
- A row **without an Mr#** whose **Treatment says checkup** ("Checkup", "checkup / pain", "xray checkup", "Check up") is a **checkup patient**. It goes to the website's **checkup list**. No patient file and no Mr# is made. When the checkup is registered as a patient on the website, the new Mr# appears in the row by itself.
- A row **without an Mr# and with any other Treatment** ("Filling & Crown prep", "RCT followup", "Monthly", "Wire check", "RCT check"), or with a **Month** filled in, is an **existing patient whose Mr# was forgotten**. It is **not** made a checkup and **not** made a new patient: the row says **Needs attention: add the Mr#**. Look the Mr# up in Healthwire and type it; the row then goes across. This also holds when a Month is typed later into a row that was a checkup: the person is taken off the checkup list (see section 5).
- A row marked **Completed** in the sheet **completes the visit** on the website. This is the owner's rule (9 Oct 2026): the website's photo, checker, doctor-group and dues checks are skipped. The visit says so ("Completed in the Google Sheet (owner rule, 9 Oct 2026)") and the website's history names "Google Sheet sync".
- **Deleting a row** in the sheet removes that visit (or checkup) from the website too: a wrong entry, or a patient who did not come (Waiting, Scheduled or No show). The website keeps it when something real hangs on it (an invoice, a photo, an x-ray, a lab case, recorded treatment): a Waiting or Scheduled visit is then marked Cancelled and the row comes back with the reason; a No show visit stays No show and its row does not come back. Section 5 has the safety rules and how to undo.
- Every night, a little after midnight, the day's list is **copied into a second spreadsheet called "Aj ki List - Archive"** (one tab per branch, with the date on every line). Then the five branch tabs are cleared, so a **new empty list** is ready for the new day. The header row stays.
- The same night the day's **checkup patients** (rows without an Mr#) are added to your sheet **"Checkup karwaliya"**, one line each, once.
- The website keeps every day too.

How it runs: a small program (a Google "Apps Script") lives inside the sheet. Every minute from 08:00 to midnight it looks at the five branch tabs, sends what changed to the website, and writes what the website changed back into the sheet. Between 00:05 and 08:00 it only does the nightly copy and clean-up.

It only touches these five tabs: **Gulshan KHI, North Nazimabad, DHA KHI, Gulberg Lhr, Islamabad**. Every other tab ("Website - ...", "Copy of DHA KHI", "Patient Response", "Daily Work", "Staff Duties" and so on) is never read or changed.

## 2. Before you start

- Use a **computer**, not a phone. Use Chrome and sign in with the Google account that **owns** the sheet.
- Best time: before staff start the day's list, or at a quiet moment.
- Have the **sync secret** ready: a long line of letters and numbers in the file named in the morning report. You paste it once. Do not send it to anyone.
- You need the program text: the file `apps-script/AajSync.js` in the project. Open it in Notepad (right-click, Open with, Notepad), press **Ctrl+A**, then **Ctrl+C**.
- For the checkup list: the Google account you sign in with needs **edit access** to the sheet **"Checkup karwaliya"**. If it does not have it, the sync still works; only the nightly checkup list is switched off, and Set up tells you so (section 7).

## 3. Steps

1. Open the Google Sheet **Aj ki List**.
2. Click **Extensions** (top menu), then **Apps Script**. A new browser tab opens. This is the "script editor" **inside this sheet**. (Do not make a separate script in Google Drive: it has to live in the sheet.)
3. On the left, under **Files**, click the **+** and choose **Script**. Type the name `AajSync` and press Enter. (If you see an older script such as `Code.gs`, leave it alone for now.)
4. A blank file opens with a few lines like `function myFunction() {}`. Click inside it, press **Ctrl+A** to select those lines, then **Ctrl+V** to paste the program text. The old lines are replaced.
5. Press **Ctrl+S** (or click the disk icon) to save.
6. At the top, next to **Run**, there is a drop-down with a function name. Choose **aajSetup**. Then click **Run**.
7. Google says **Authorization required**. Click **Review permissions** and choose your account.
8. Google says **"Google hasn't verified this app"**. This is normal, because it is your own private script. Click **Advanced**, then **Go to ... (unsafe)**, then **Allow**.
   - It asks to: see and change your spreadsheets (to read the five tabs, make the archive and add to the checkup list), connect to an external service (to talk to the website), and run when you are not there (the one-minute timer).
9. **Go back to the Google Sheet browser tab.** The questions appear there, not in the script editor.
10. A box says **Paste the sync secret from the file you were given**. Paste it and click **OK**. (The secret is typed into this box only. It is not written into the script text, and you never put it into "Script Properties" or "Project Settings".) If you run Set up again later and a secret is already saved, a box asks **Keep the saved sync secret?**: say Yes, or say No to paste a new one.
11. For each branch tab that already has patients on it, a box says how many patients are on the tab (with the first and the last name) and asks **"Which day are they from?"**
    - **Leave it empty and click OK**: the patients are **today's**. They are matched to the website's patients of today. Nobody is doubled. Where the website already has the patient today, what front desk did there this morning stays: a patient front desk **cancelled** or marked **No show** stays so, and a waiting patient keeps the website's treatment and details (the row shows "⚠ Website change kept for: ..." and the sheet's cells take the website's text). The status still only moves forward: a row marked **Completed** (or Treatment) completes the website's Waiting visit (owner rule), it is never set back to Waiting. What staff type into a row after Set up counts as usual. If some of the rows are already marked **Completed**, the box asks once more ("Are these really today's patients?"), because a list with Completed patients is usually a day that has finished and today's answer would make every one of them a visit of today. Click **No** to be asked for the day again, and type it.
    - **Type a day**, like **06-10-2026** (day-month-year): the patients are from that earlier day. Those rows are copied to the archive under that date and the tab is cleared. Nothing is added to the website, and that day can be brought in later (section 9).
    - **Cancel**: stops the setup. Nothing more is changed. You can run it again.
    - A tab with no patients on it is simply marked as today's.
    - Each tab keeps the **last day the branch was open**. A branch that was closed yesterday still shows its last open day; at night only a tab with rows is archived, under its own day.
12. A box says **Found 1 other timer(s) ... They are probably the old copy into the "Website - ..." tabs. Turn them off?** Click **Yes**. (If you are not asked, there was no old timer in this script. See section 10.)
13. A box says **Done.** with a link to the archive. If the checkup list cannot be reached, the box says so below that line.
14. **The Status drop-down.** In all five tabs the Status column has a drop-down list with only Scheduled, Completed, Waiting and Treatment. Staff also need **Cancelled** and **No show**, and the website writes those two words into the cell. In each tab: click the Status column's letter, click **Data**, then **Data validation**, click the rule, add the two items **Cancelled** and **No show**, and click **Done**.

If something stops half way, just run **aajSetup** again. It is safe to run any number of times.

## 4. How you know it worked

- Every branch tab has a new column at the right called **Website**. The heading reads **Website · 09:15 ✓** (the time of the last check). Three more columns next to it (**Sync key**, **Sync base**, **Sync edited**) are hidden. They are how the sheet remembers each patient. Never delete or unhide them.
- Row 1 of every branch tab has **filter buttons** (a small triangle in each heading). Set up adds them, and they reach over the hidden columns too, so sorting with them moves whole rows. A filter that was already there is kept with what it shows; it is only made wider when it did not reach the hidden columns. If someone removes the filter, the sheet puts it back within about ten minutes.
- Within 2 minutes the rows show **✓ On website** in the Website column.
- The website's Aaj ki List shows the same patients as the sheet. Checkup patients show on the website's checkup list.
- A new menu **Aaj Sync** appears next to Help. A new tab **Aaj Sync log** lists what the sync did (new patients added, removals, problems).
- In Google Drive there is a new spreadsheet **Aj ki List - Archive**.

## 5. For staff: one page

- Type patients in the sheet or on the website, as before.
- **With an Mr#** the row is a patient. **Without an Mr#** the row is a checkup patient (no patient file) **only when the Treatment says checkup**; with any other Treatment the row asks you to add the Mr#. A stray dot after the Mr# ("8602.") is ignored. Website Mr# numbers are **50000 and above**; a number below 50000 is a Healthwire number. A Healthwire number the website does not have yet makes a new patient file only up to a limit: **100 above the highest Healthwire number the website already has, plus 10 for every day since Healthwire registered that patient**. Healthwire gives about 5 new numbers a day, so the limit keeps ahead of it, and new Healthwire patients typed in the sheet keep going across between Healthwire imports. A number above the limit has not been given by Healthwire yet, so it is almost always a typing slip (9988 typed for 9898): the row says **"looks like a typo"** and nothing is made. (Otherwise the slip would become a patient file, and when Healthwire later gives that number to a real patient, that patient's records would be copied into the wrong file.) When new Healthwire numbers come within 20 of the limit, the row of a new patient also says so: ask Dr. Ali to import the latest Healthwire patients. **Old numbers:** the 11 patients the website numbered 10000-10012 now have 50000-50012, and a number that was merged into another patient file is not used any more. If such an old number is typed with that patient's **whole name** (the same surname), or with **their phone and their first name**, the row says which Mr# to use and nothing is saved. With any other name, even the same first name with another surname ("Ali Raza" typed with the old number of "Ali Khanzada"), it is a **new Healthwire number**, because Healthwire will give 10000-10012 to new patients soon: the new patient gets their own file, never the old patient's (once Healthwire has come near that number; before that the row says "looks like a typo", like any number far above Healthwire's highest).
- **When the name does not match the Mr#.** The website links a row to a patient only when the name in the row is clearly that patient (the same first name, or an everyday spelling of it, and no other surname). If the name is only partly the same (another surname, a slip, another first name), the row is **not saved at all** and says **"Needs attention: the name in this row does not match Mr# ..."**. Nothing goes onto that patient's file or onto her visit of today, so a wrong Mr# can never complete, change or move somebody else's visit. Check the Mr# (the most common mistake), or type the name the way the website has it. As soon as the row is right it goes across by itself. The same message appears on a row that was already on the website when another person's name is typed over it: nothing from that row is taken until the name (or the Mr#) is put right.
- **Names spelt differently from the website are refused.** If the website has "Fahad" and the row says "Fahd" (or "Humza" for "Hamza", "Hafza" for "Hafsa", "Zainab" for "Zenab"), the row is refused with "the name in this row does not match Mr# ..." until staff type the name exactly as the website has it. This is on purpose: two different people can have those names (a Fahd and a Fahad, like brothers Umar and Umair), and a row typed with the wrong Mr# must never land on somebody else's file. Look the patient up on the website and copy the spelling; the row then goes across by itself.
- **A checkup (or visit) moved on the website.** When front desk corrects the **Branch** of a checkup on the website's Checkups page (or a visit is moved to another branch or day), the checkup is **not** deleted. It appears in the other branch's tab as "✓ Added from the website", and its old row says "deleted on the website" (or "moved to another branch or day"). Delete the old row: nothing is removed from the website.

| ✗ Patient name is too short. | The name cell has one letter or none. Nothing was looked up or saved. | Type the patient's name. |
| ✗ Too many new patients from the sheet today. Add this one on the website. | The sheet may add at most 30 new (Healthwire) patients per branch and day (a safety limit). | Add it on the website. |
| ✗ Too many patients added from the sheet today. Add this one on the website. | The sheet may make at most 120 visits per branch and day (a safety limit; the busiest tab has about 50 rows). After that every new row with an Mr# gets this answer, whatever the Mr# (only a patient already on today's list is still found). | Add it on the website. |
| ✗ Too long: ... | A cell has too many letters. | Make it shorter. |

- **Status** words the sheet understands: Waiting, Treatment, Scheduled, Completed, Cancelled, No show (Dr. Ali adds the last two to the drop-down, section 3 step 14). An empty Status is filled in by the website. A word it does not know stays as typed and the row asks you to use one of the words above.
- **Completed** in the sheet completes the visit (owner rule). Anyone who can edit the sheet can do this, so mark Completed only when the patient is really done.
- **Token, Group and Month** can hold your own words ("Kit 80k", "Group 1, Group 2", "04 Photo"). They stay exactly as you typed. The website only reads a Token that is a plain number. In the **Lahore and Islamabad** tabs the Token column holds kit and material text: the website **never fills a blank Token cell there** and never writes a token number into it, and a plain number typed there ("2" units) is kept as text, never taken as a token. In the other three tabs a blank Token cell is filled with the website's token for that patient. A patient added to the Lahore or Islamabad tab from the website comes without a token number in that cell.
- **P.P, Healthwire and Reminder** belong to the sheet. The website never writes over them.
- **Wait a minute after typing a new row.** A row you are still typing in is never touched. A new patient is sent to the website a minute after the last key.
- **Take a patient off the list** by setting Status to Cancelled, or by deleting the row.
- **Deleting a row** (or clearing its cells) removes the visit from the website only when it is Waiting, Scheduled or No show and nothing is attached to it. A checkup goes the same way only when it is Waiting or No show, has no follow-up notes and is not registered as a patient: a checkup in **Treatment** or **Completed** is kept, with its doctor and details, and its row comes back (owner's rule: a deleted row is a wrong entry or a person who did not come). (A checkup row that became a patient's visit because an Mr# or a Month was typed into it is different: see section 5.) A deleted row never comes back by itself, unless the website kept the visit and says why in the row (the table above), or the visit is set to work again on the website later (next point).
- **A Cancelled patient whose row you delete** stays off the sheet and stays Cancelled on the website. If front desk later sets that patient back to Waiting on the website (the patient came after all), the row comes back by itself ("✓ Added from the website"); the old deletion never removes that visit. If you type the patient again yourself, the new row takes over the same visit: it becomes Waiting (or whatever Status you typed) with what you typed. These safety rules always hold:
  - Deleting **4 or more rows at once**, or **a quarter or more of a tab** (2 or more rows), is treated as a mistake: nothing is removed from the website, and all the rows come back with "Needs attention".
  - At most **15 removals per branch per day**. After that, rows come back.
  - A tab that suddenly reads empty never removes anything.
  - Every removal is written to the website's history (name "Google Sheet sync", with the whole row).
  - What the sheet itself made from that row the same day goes with the visit when nothing else hangs on it: the **patient file** of a new Healthwire Mr# typed in the row, and the **braces case** the row's Month started. (This is what happens when staff correct a mistyped Mr#: the row is sent again with the right number, and the file made from the wrong one is removed.) A patient file that **somebody has changed on the website since** (front desk filled in the history, allergies, consent, date of birth or address while the patient waited) is **kept**, and the log says so ("... is kept: details were saved on it on the website. Check it"). Ctrl+Z and the undo below put them back too.
  - **To undo a deletion**: press Ctrl+Z in the sheet right away. The row comes back with its hidden key and the website puts the visit back. (A row typed again from scratch is a new row, not an undo.) If the visit cannot come back (for example its braces case was deleted on the website in the meantime, or the patient was typed again in another row and is on the list there), the row says "This visit was deleted on the website. Delete this row." straight away and everything else keeps working. The old visit does not come back later by itself (not even when the other row is deleted); delete the row that says so. Dr. Ali can also undo it later from the SQL editor: `select public.aaj_undo_removal(<the number of the SHEET_REMOVED line in the website's history>);`
  - **Ctrl+Z after the sheet already put the rows back** (the rows came back with "Needs attention: ... rows disappeared at once", or with "Kept on the website and marked Cancelled"): your rows come back at their place and the rows the sheet put back stay at the bottom, so each patient is there twice. The lower row says **"Duplicate of row ..."** and is not sent: nothing is made twice on the website (no second checkup, no second visit). Delete the duplicate rows, one at a time or all together: nothing is removed from the website. A visit that was kept and marked Cancelled goes back to the status it had (Waiting or Scheduled), unless somebody changed it on the website in between.
- **A row is the person in it.** The sheet tells people apart by the whole name and the phone, not by the first name alone (many patients share one: Ali, Ayesha, Fatima), and not by the phone alone (a family shares one).
  - Correcting the phone (same name) keeps the same checkup, unless another row now holds that same name with the old phone (then the two people were swapped, see below). Correcting the surname, or a small slip in the first name ("Ayesha" / "Aysha"), with the same phone keeps it too. (A checkup already **registered as a patient**, whose row shows an Mr#, only takes a name that fits that patient; another surname there says "Needs attention" and nothing is saved.)
  - **Another first name** in a checkup row is **another person**, even on the same phone (sisters Amna and Zainab share their mother's number): the row becomes a new row and that person gets their own checkup. So to correct a first name that was typed completely wrong, correct it on the website's **Checkups** page instead.
  - While somebody is still typing in a row (the last key less than a minute ago), a change to its **Mr#, name or phone** is not sent yet. Staff often type a new person over a row one cell at a time; the sheet waits until the row is quiet and then looks at the whole row. A row typed over with somebody else becomes a new row: the person who was there keeps their checkup (or visit) and follow-up notes on the website. Their checkup is removed from the website like a deleted row when nothing hangs on it, otherwise their row comes back.
  - Sorting only some of the columns, or cutting and pasting only the visible cells, moves people away from their hidden keys. Each row then finds its own visit or checkup again (by the Mr#, or for a checkup by the same name and phone, or, when it has no phone, a checkup of that name whose row is not on the tab any more, whatever its Treatment says). Nothing is removed and nothing is doubled. This also holds when the sort happens while the website is still answering a row that was just typed: that patient finds their new visit again in whichever row they are now. It also holds for brothers or sisters on **one phone whose first names look alike** (Ali Raza and Ali Hamza, Hassan and Hussain): when another row holds a person's exact name and phone, that row is the person, so the sort cannot swap their checkups or notes.
  - When rows only **changed places** (a sort of the visible columns, or the sort button of a filter made before Set up), each row takes over the hidden key of the person now in it, and nothing is sent. So two rows with the **same Mr#, name and phone** (a checkup registered as a patient and that patient's visit of the same day) are not mixed up, and neither are two walk-ins with the **same name on different phones** (two "Ayesha" rows): each keeps its own treatment, Month, status and follow-up notes. A row that says **"deleted on the website"**, or a row the website could not place (✗, for example a wrong Mr#), moves with its person too: nobody else's visit is removed because of it, the deleted visit is not made again, and the ✗ message stays on the right person. **Two walk-ins with the same name and no phone** (two "Sana" rows) stay two checkups however often the tab is sorted, and a row with its **"Duplicate of row N"** copy stays one patient: after the sort the lower one still says "Duplicate of row ...". A row that says **"Left over from ..."** keeps that message on yesterday's patient after a sort: it never moves onto a patient of today, nobody's visit is removed because of it, and yesterday's patient is not sent. All of this also holds when a wrong entry is removed with **Delete cells, shift up** (only its cells, not the whole row), when a row's cells are cleared and the tab is then sorted, and when a row's cells are cut and pasted lower down. One case the sheet cannot sort out: **two walk-ins with the same name and no phone** where one of them also has a "Duplicate of row N" copy. A sort can then make an extra checkup, so delete "Duplicate" rows before sorting.
  - A row that says **"deleted on the website"** belongs to that person only. If a different patient is typed over it, it becomes a new row for that patient.
  - A checkup row that was registered as a patient (the website wrote the Mr# into it) whose Mr# is cleared is a new row: it finds its checkup again by name and phone, or, if somebody else was typed over it, that person gets a checkup of their own and the registered checkup keeps its patient. Another Mr# typed into it with the same name is a slip: the website writes the registered Mr# back (⚠, table above).
  - An **Mr# typed into a checkup row** makes the row that patient's visit when the website has that patient and the name matches (an existing patient who came for a checkup, whose Mr# you looked up in Healthwire): the row says "sent again as that patient's visit", lets go of the checkup within a minute and the visit is made. The checkup is taken off the website, also when it is in Treatment or Completed (the person is a patient, not a checkup to call back), unless it has follow-up notes: then it is kept and its row comes back. The person is not put on the nightly checkup list. The log says so, and Dr. Ali can undo it. If front desk had already registered the person on the website with that Mr#, the row simply stays that checkup (no visit) and shows ✓. Any other Mr# (a slip, a number the website does not have) leaves the checkup as it is and the row says "Needs attention: ... this row stays a checkup": a slip in the Mr# cell never removes a checkup and never makes a patient file.
  - **Typing a patient who is already on today's list on the website** (front desk added them, or a Cancelled patient came after all) takes over that visit, nothing is doubled. What you typed wins where you typed it after the website's last change; the status only moves forward (Waiting, Treatment, Completed), and a Cancelled or No show visit becomes the status you typed (Waiting when you left Status empty). A patient already in Treatment or Completed keeps what the website has. The website's token, Month and Group stay too (when it has them).
  - A **Month** typed into a checkup row does not: a person with a Month is a braces patient, never a checkup (owner, 9 Oct 2026). The row says it is sent again as a visit, and a minute later it is a new row. Without an Mr# it says **Needs attention: add the Mr#**, and the checkup is taken off the checkup list, also when it is in Treatment or Completed (unless it has follow-up notes: then its row comes back). Type the Mr# from Healthwire and the visit is made. If the checkup was already registered as a patient (its Mr# is in the row), the visit is made for that patient straight away, and the checkup is kept as it was and comes back as its own row.
  - A visit row whose Mr# is cleared by mistake stays the same visit; the website writes the Mr# back. **The same when another Mr# is typed into it while the name stays the same** (a token number typed into the Mr# cell, a digit too many): the visit and everything front desk added to it stay, nothing is removed or made, and the website writes its own Mr# back (⚠, table above). Only a new Mr# **with another name** is another person: the row becomes a new row for them. One exception: when the sheet itself made the patient file from that very row today (a new Healthwire Mr# typed with a slip) and the corrected number is one or two digits away from it (9888 corrected to 9878), the row is sent again with the right number, and the file made from the slip is removed with its visit (unless front desk saved details on it), also when that visit is already Completed or in Treatment. When an invoice, a photo or a checker is already on that visit, the number is written back instead and the row says to correct the patient file on the website. Any other change of that Mr# is written back like a slip; if the number was completely wrong, delete the row and type the patient again in a new row. A row with no Mr# that now holds somebody else (another name and phone, for example after sorting only some columns) becomes a new row and never changes the visit that was there.
  - Best: do not sort the five tabs. If one must be sorted, **use the filter buttons in row 1** (click the small triangle in a heading, then **Sort A to Z** or **Sort Z to A**): they move whole rows, hidden columns included. Do **not** select only some columns and sort them (Data, Sort range): that leaves the hidden columns behind. The sheet sorts that out by itself too, but it is better not to rely on it. (Selecting whole rows by clicking the row numbers on the left before Data, Sort range is also fine.)
- **The heading time** (for example "Website · 09:15 ✓") should be recent. If it is older than **10 minutes** during clinic hours, tell Dr. Ali.
- The heading can also say: **✗ not syncing: the website did not answer** (the internet or the website is down; it starts again by itself), **the website is busy, trying again** (it starts again by itself), **✗ sync secret not accepted** (Dr. Ali must run Set up again), **paused for today (Google time limit)** (use the website; see section 11).

## 6. At night

- At **00:05** the script waits until nobody has typed for a minute (at most until 00:30), sends the last changes to the website for the old day, copies every row of a tab that has rows (every column, also a column you added to the right of the Website column) into **Aj ki List - Archive** (one tab per branch, the date of **that tab's own day** in the first column), and clears the tab. The header row stays. The heading then reads **new list for 2026-10-10**. A tab with no rows is left alone.
- A row copied whole that nobody deleted (it says **"Duplicate of row N"**) is archived and cleared like the others, together with its original. A row of an earlier day that is still on the tab the next morning says **"Left over from ... : delete this row"** and is never sent as a patient of the new day; the next night clears it without copying it again.
- Then the day's **checkup patients** are added to the sheet **Checkup karwaliya**. A checkup patient is a row the website filed as a checkup (it stays one after the person is registered and gets an Mr#), or a row with no Mr# and no Month whose Treatment says checkup. Rows marked **Cancelled** or **No show** are left out, and so are rows whose checkup was **deleted on the website**, rows that "need the Mr#", and **every row with a Month** (a braces patient, even if the row started as a checkup; the log names such a row). A checkup row that became a patient's visit because a matching Mr# was typed into it (section 5) is not a checkup any more and is left out; a checkup row that still shows a refused Mr# ("this row stays a checkup") is still a checkup and is listed. A second row of the same checkup patient that was refused as "Already on this list in row N" is not listed (the person's own row is). The lines go to the tab "Aj ki List checkups" (made if it is not there). Each line has: Month, Patient Name, Phone, City, Clinic, Doctor, Treatment / Checkup For, Est. Fee (Rs) empty, Status **Not Contacted**, Notes, Source Tab ("Aj ki List - Gulshan KHI" and so on). A hidden last column ("Sync id") makes sure a patient is added only once. **Lines already in that sheet are never edited or deleted.**
- If the website cannot be reached at midnight, nothing is cleared: the script keeps trying every minute until 02:30 so that the last rows reach the website first. After 02:30 it copies and clears anyway (everything is in the archive).
- A row that still showed ✗ at midnight (for example "add the Mr#" or a wrong Mr#) never reached the website. It is archived with the others, and the **Aaj Sync log** names each such patient ("Archived without reaching the website"). Correct the row in the archive and bring that day back with **Admin, Import** (section 9).
- A row that said **"deleted on the website"** (or "moved") at midnight is different: front desk deleted that visit or checkup on the website on purpose (a wrong entry, or a patient who did not come), or moved it to another branch. The log names it as "Deleted on the website ...", **not** as "never reached the website". In the archive its **Website visit id** column says **deleted on the website**, and Admin, Import skips such rows, so a wrong entry never comes back as a completed visit. It is not put on the checkup list either.
- In the archive the **Website visit id** column holds the website's visit number for a patient's row, and "checkup ..." for a checkup patient's row. Admin, Import skips the checkup rows too (a checkup is never a visit; it is on the website's Checkups page already).
- If a crash happens in the middle, the next minute finishes the job. Rows typed after the copy are kept for the new day. If the sync was off overnight, rows typed this morning are **not** archived under yesterday: they stay on the tab as today's patients.
- If the sync was off for a day, the old rows are still archived the next morning under their old date. They are not added to today.
- Open the archive from the menu: **Aaj Sync, Open the archive**.

## 7. The checkup list ("Checkup karwaliya")

To use another tab or another sheet, open the script editor, **Project Settings**, **Script Properties**, and add `CHECKUP_TAB` (the tab name) and/or `CHECKUP_SHEET_ID` (the sheet id from its address). These two are not secret.
- If the tab already has a header row, the script finds the columns by name ("Patient Name", "Phone", "Month", "City", "Clinic", "Doctor", "Treatment / Checkup For", "Est. Fee (Rs)", "Status", "Notes", "Source Tab"). A tab without a "Patient Name" column is not used.
- If the sheet cannot be opened (no access), nothing is lost: the lines wait in the script (up to 300), the sync itself keeps working, the menu **Aaj Sync, Status** says "Checkup list not updated ...", and the lines are added as soon as access works. Share the sheet with edit access to the Google account that ran Set up, then run **Set up** again (or just wait).

## 9. Bringing an old day back into the website

1. Open **Aj ki List - Archive**.
2. Click **File**, **Download**, **Microsoft Excel (.xlsx)**.
3. On the website go to **Admin, Import**, section **4. Aaj ki List history**, choose the file, and import the day you want. The Date column tells the website which day every row belongs to.
   - The import **never guesses who a row is**. A row with an Mr# is that patient **only when the name in the row fits that patient without doubt** (the same check as the sync: the same first name or an everyday spelling of it, and no other surname). A row typed with **another patient's Mr#** (the sync refused it with "Needs attention: the name in this row does not match Mr# ..." and nobody fixed it before midnight, so it is in the archive as it was typed) is **not** put on that patient's file: no visit and no braces case. It is listed at the end with the reason **"Mr# belongs to another patient"**. A row whose name only **partly** matches (the right first name with another surname, a slip or another first name, or another name with the patient's phone) is **not** put on that patient's file either: it is listed with the reason **"the name only partly matches Mr# 25001 (Ayesha Khan): ... Check the Mr# or the name"**. Correct the Mr# or the name in the file and import it again. An Mr# the website does not have is never put on somebody else's file, even when the name or phone is the same. A row **without an Mr#** is matched only when its phone **and** first name fit exactly one patient, and never when the surnames differ ("Ali Raza" is not his brother "Ali Hamza" on the family phone: listed with **"add the Mr# (another person with this first name is on this phone)"**); a row matched by the first name only gets the "check the Mr#" note and no braces case; a name alone is never enough. Rows it cannot be sure of are listed at the end as "could not be matched": correct the Mr# in the file (look it up in Healthwire) and drop the file again.
   - The box **Add patient records** adds a patient only for a **Healthwire Mr# (below 50000)** that the website does not have yet, and only up to the same **Healthwire limit as the sync** (section 5: 100 above the highest Healthwire number the website has, plus 10 for every day since Healthwire registered that patient). A higher number is listed with the reason **"an Mr# above the newest Healthwire number the website takes (9998): probably a typo ..."**: check it, or import the latest Healthwire patients first and import the day again. A row **without an Mr#** never becomes a patient file, and an Mr# of **50000 or more** that the website does not have is a typing mistake and is never added.
   - Rows of the archive marked **deleted on the website** or **checkup** in the "Website visit id" column are skipped (section 6); the import page says how many.
   - It never makes a **second file for a patient the website already has**. If the row's exact name and phone are already filed under another Mr#, the row is listed with the reason **"this name and phone are Mr# 30010"**. If the row has an **old number** of a patient (one of the website's 10000-10012, now 50000-50012, or a number merged into another file) with that patient's whole name (or their phone and first name), it is listed with **"Mr# was renumbered to 50003"** or **"Mr# was merged into 30010"**. The other rows with that same Mr# in the file are held back with it ("held back with the other row of this Mr# ..."). Correct the Mr# in the file and import it again. An old number typed with **another** person's name (also the same first name with another surname) is treated as a new Healthwire number.
   - **Checkup patients** of that day (rows without an Mr# whose Treatment says checkup) are **not** imported as visits: the page counts them and leaves them out. They were already added to "Checkup karwaliya" at night. Most of them are on the website's checkup list already (the sync put them there during the day). To bring the others onto it (for example a checkup row that still needed attention at midnight), open the tab **"Aj ki List checkups"** in "Checkup karwaliya", click **File**, **Download**, **Comma-separated values (.csv)** (this downloads only that tab; the import reads the first list it finds in a file), and use that file in **Admin, Import**, section **5. Checkup list**. You can import the whole tab: a line whose person, month and branch are already on the website's checkup list (put there by the sync, or entered on the website) is skipped with the reason **"Already on the website (the Google Sheet sync put this checkup there)"**, so nobody gets a second checkup record and the follow-up notes stay on the real one. Only lines that never reached the website are added.

## 13. Safety: who can do what (please read)

- **The script is inside the sheet.** Anyone who can **edit** the sheet can open Extensions, Apps Script, and can change the script. The timer runs as **you** (Dr. Ali). A person with edit access who changes the script could therefore make it use your sync secret. The secret is **not** stored in the script text or in Script Properties (where every editor can read it in plain sight); it is kept in your own private storage. That makes it harder to find, but it does **not** make it safe against an editor who wants to misuse it. Because the script opens the archive and the "Checkup karwaliya" sheet, Google gives it access to **every spreadsheet your Google account can open**, not just these three; an editor who changes the script reaches all of them too. Give **edit access to the sheet only to staff you trust.** (Safer, if you can: run Set up from a separate Google account that can open only these three sheets.)
- The secret is small on purpose. It lets the sheet read and change **today's** lists of the five branches on the website (and yesterday's until 03:00, for the last sync before the archive). It cannot search the patient list, it cannot read other days, and what the website sends back is only what the sheet already shows. When a typed Mr# is refused, the answer never says whose Mr# it is. A typed Mr# is linked to a patient only when the name in the row is clearly that patient (the patient's first name or an everyday spelling of it, and no other surname; a Muhammad, Syed or Hafiz counts as part of the name); a name that only partly fits, a guessed Mr# with a surname alone or with a first name and a title ("Muhammad Usman" for "Usman Tariq"), an unreadable or empty name, a "name" of more than four words (unless it is the patient's whole name exactly), or another name with the patient's own phone links nobody and gives nothing back. A partly fitting name gets exactly the same answer as a wrong one, so the answer never tells whether the first name (or the phone) was right. A name of one letter is answered "too short" before anything is looked up. The sheet can make at most 120 visits and 30 new patients per branch and day, a new patient only with a Healthwire Mr# within the Healthwire limit of section 5 (a number Healthwire has not given yet never becomes a file that a real Healthwire patient is later copied into), and at most 20 calls a minute are accepted. Once the 120 visits of a day are made, every new Mr# row gets the same answer, right name or wrong. Every refused lookup is written to the website's history (with the Mr# that was typed and a fingerprint of the typed name and phone): the same row sent again counts once, but every new guess (another name or phone for the same Mr#) counts again. At most five are answered in one call. After 200 in a day, every new Mr# row gets one and the same answer, right name or wrong, and nothing more is made from the sheet that day (a patient already on today's list is still found), so the limit cannot be used to try names for free. Calls are limited in number and size. Everything the sync does is written to the website's history under "Google Sheet sync".
- **Who "approved" a Completed row.** The visit's reason text says "Completed in the Google Sheet (owner rule, 9 Oct 2026)" and the history names "Google Sheet sync". The website's own "approved by" columns (`protocol_override_by`, `dues_override_by`) must hold a real staff account, so they hold Dr. Ali's account; no screen shows them. Nobody has really approved those rows by hand.
- The sheet's **Completed** completes a visit on the website without the photo, check and dues rules (owner rule). Anyone with edit access can therefore complete a visit. The history shows it every time.
- A person with edit access can **delete rows**. Deletions are limited and audited (section 5) and can be undone, and nothing with an invoice, photo or treatment is ever removed. A visit whose row was deleted while it was Cancelled is never removed later by that deletion.
- **If a staff member with edit access leaves**, ask for a **new secret** (the website then stops accepting the old one) and run **aajSetup** again with it.
- The script never deletes a patient file, with one exception: a file that the sheet itself made from a row **the same day** (a new Healthwire Mr#), when that row is deleted or its Mr# is corrected, nothing else hangs on the file and **nobody has changed it** on the website since it was made (a file front desk filled in is kept). That file is kept in the website's history and comes back with Ctrl+Z or the undo. Otherwise the script removes only a visit or a checkup that was deleted from the sheet (and a braces case that row's Month had just started), as described above.
